# CCA-002 worker container security review

The current Docker Desktop 4.82.0 / Engine 29.6.1 / WSL2 kernel 6.6.87.2 host rejected a trusted namespace prerequisite probe inside a default-seccomp container with `PermissionError: Operation not permitted`. The user explicitly approved testing the scoped worker profile in this session. The final tested profile and corrected setup details are described below. The application must remain disabled unless the full sandbox checks succeed. A different deployment requires review of its actual profile and environment.

## Concrete proposed change

Apply only [compose.reviewed.yaml](../deploy/worker/compose.reviewed.yaml) on top of [compose.yaml](../deploy/worker/compose.yaml), using [docker-seccomp.json](../deploy/worker/docker-seccomp.json). This affects newly created `contest-check-worker:cca002` containers only. It does not alter the daemon, host sysctls, other services, or existing containers.

Retained boundaries: non-root UID/GID 1000, all capabilities dropped, no-new-privileges, read-only root, network mode `none`, no published ports, no host bind mounts, no Docker socket, no application/model secrets, 384 MiB memory with no additional swap, one CPU, 16 outer processes, and one private 96 MiB tmpfs. The one-shot worker receives bounded typed JSON on stdin and produces a result on stdout; it has no network server or arbitrary command/path field.

The outer profile defaults to EPERM and targets Linux x86-64. Its namespace-related allowance is the exact legacy `clone` flag value `0x7e020011` (USER/MOUNT/NET/PID/IPC/UTS/CGROUP plus SIGCHLD). It permits `0x4111` and `vfork` for the trusted Python supervisor to launch NsJail, and `0x1200011` for Docker's init process to start/reap the worker. All remain subject to the 16-process outer cap. `clone3` returns ENOSYS so NsJail uses the inspectable legacy flag arguments. `unshare` and `setns` remain denied. Mount/pivot/chroot, UID mapping, capability dropping and seccomp installation calls support NsJail setup inside the newly created unprivileged user namespace. They grant no host capabilities. Socket creation is limited to AF_UNIX and the specific local Netlink query below; the outer worker has no interface other than loopback and no outbound network.

During testing, NsJail 3.5 was found to unconditionally query route interfaces while creating a network namespace. The outer profile therefore additionally permits only AF_NETLINK with protocol NETLINK_ROUTE (0), plus bind/getsockname for that local kernel query. No AF_INET/AF_INET6 sockets, network interfaces, capabilities or egress are added. Route changes remain prohibited by the absence of network-administration capabilities. The inner policy denies all socket families, including Unix and Netlink.

The legacy mount path failed its read-only root remount under nested user namespaces. The selected backend explicitly uses NsJail's `--experimental_mnt new` path with Linux `fsopen`, `fsconfig`, `fsmount`, `open_tree`, `move_mount` and `mount_setattr`; these setup calls are allowed only by the outer profile and denied inside the jail. Read-only mounts are retained. There is no automatic fallback to writable mounts or to a different execution backend. A host lacking the required new mount API must fail qualification. This uses upstream's experimental mount implementation, which must be included in deployment review and the recorded host-specific evidence.

These setup syscalls remain an added kernel attack surface. A separate default-kill Kafel policy is installed inside every jail before Python starts, allowing Python file I/O and memory operations while denying network, fork/clone, ptrace, mounts, namespace changes and privilege-management syscalls. The inner jail receives a minimal read-only CPython runtime, only one participant's allowlisted `.py` files, one read-only input file, and one writable pre-created output file. No host root or full application tree is mounted into it.

## Required evidence before acceptance

Pinned NsJail and Kafel build/integrity checks; observed outer resource/security settings; nested user/mount/network/PID/IPC/UTS/cgroup namespaces; non-root jail UID; no capabilities; no-new-privileges and layered seccomp; no network/DNS/host-file access; read-only sources/input and only the expected writable output; memory, CPU/wall, output/file-descriptor/process limits; termination/reaping and cleanup. Trusted benign probes must all pass before the same worker process accepts any submitted program. Environment flags and saved verification files cannot bypass that gate.

The default deployment does not apply this override automatically. A failed check produces structured `system_error` metadata and refuses submitted programs. No `--privileged`, `seccomp=unconfined`, added SYS_ADMIN capability or writable host-cgroup mount is proposed.
